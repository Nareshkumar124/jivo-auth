How it works

  1. Sign in. Your frontend sends the email and password to {{ facts.base }}/api/v1/auth/login/ and gets an access token ({{ facts.access }}) and a refresh token ({{ facts.refresh }}).
  2. Call your API. Every request to your DRF API carries Authorization: Bearer <access token>.
  3. Verify locally. Your API checks the token itself with the jivo-auth-client package: signature, expiry, issuer, and that {{ slug }} is in its apps claim. There's no call to this service per request.
  4. Refresh. When your API answers 401 because the access token expired, the frontend exchanges the refresh token for a new pair and retries.

Your API never sees passwords. The package fetches this service's public key once from {{ facts.jwks_url }} and keeps it in memory, so your API keeps working through short outages here. Access is per application: a user whose token doesn't list {{ slug }} gets 403 from your API, however valid the token is.

Protect your views

With the settings above, every view needs a valid token. Opt out explicitly where a view is public:

{% include "adminpanel/partials/code.html" with code=samples.views label="views.py" id="code-views" %}

Requests without a usable token are rejected before your view runs:

StatusdetailThe client should
401Authentication credentials were not provided.Sign in.
401Token has expired.Refresh, then retry once.
401Invalid token.Refresh; if that fails, sign in again.
401Invalid authorization header.Fix the bug: send Bearer <token> with one space and no quotes.
401Access token required.Fix the bug: it sent the refresh token.
401User account is disabled.Only with LOCAL_USERS: the local record is deactivated.
403Your account does not have access to this application.Show "no access". Refreshing won't help until access is granted.

JivoJWTAuthentication only handles Authorization: Bearer …; other schemes are left to other authentication classes, so it combines with, for example, SessionAuthentication. With drf-spectacular, the package registers a jivoAuth bearer scheme, so your Swagger UI's Authorize button takes a Jivo access token.

Who is the user?

By default request.user is a JivoUser built from the token, without any database query:

{% include "adminpanel/partials/code.html" with code=samples.who_am_i label="views.py" id="code-me" %}
AttributeValue
id, pkThe Jivo user ID (uuid.UUID), the token's sub
emailVerified, lowercase
appsTuple of application slugs; has_app("{{ slug }}") checks one
claimsThe whole verified token payload
is_staff, is_superuser, has_perm()Always false: permissions belong to your app

request.auth is the raw token, for forwarding to another Jivo API. The token doesn't carry names or the employee code; read those from GET /api/v1/users/me/ or the user lookup.

Local users: real foreign keys

With LOCAL_USERS, request.user is a row of your AUTH_USER_MODEL, created on the user's first request with the Jivo ID in username, the token's email and an unusable password. Deactivating that row blocks the user in your API only. The token's claims are on request.user.jivo_claims.

{% include "adminpanel/partials/code.html" with code=samples.local_users label="settings.py / models.py" id="code-local" %}

An API that already has users

Keep its user table, so foreign keys and app data stay as they are, and add an auth_id = models.UUIDField(null=True, blank=True, unique=True, editable=False) column. Export the users (ID, email, names, password hash) to JSON, then on this server run manage.py import_users {{ slug }} users.json > mapping.json, with --dry-run first. Verifiable password hashes are kept, emails that already have a Jivo account are linked to it, and the output maps each source_id to a Jivo ID. Store those in auth_id, then set "LOCAL_USER_ID_FIELD": "auth_id" and "LOCAL_USER_LINK_BY_EMAIL": True. The integrate-jivo-auth Claude Code skill in the repository walks through every step.

Frontend

The frontend signs in, refreshes and signs out at this service, and sends the access token to your API. This client refreshes once for any number of failing requests, shares tokens between tabs, and signs the user out when the session has ended:

{% include "adminpanel/partials/code.html" with code=samples.frontend label="auth.js" id="code-frontend" %}
  • Store both tokens after every refresh. The refresh token that was sent keeps working for {{ facts.grace }} seconds, which covers requests already in flight. Sending it after that is treated as theft and ends the session.
  • Where tokens live. localStorage survives reloads but any injected script can read it, so keep a strict Content-Security-Policy. On mobile, use the Keychain or Keystore.
  • Changes take up to {{ facts.access }}. After an administrator removes access or the user changes their password, your API accepts the current access token until it expires; the next refresh then fails or drops {{ slug }}.
  • Forgotten passwords: link to {{ facts.base }}/forgot-password/{% if status.email_state == 'missing' %} (it needs email, which isn't configured yet){% endif %}.

Go-live checklist

  • JIVO_AUTH["URL"] is exactly {{ facts.base }}.
  • JIVO_AUTH["APP"] is {{ slug }} and python manage.py check is clean.
  • Your server can reach {{ facts.jwks_url }} over HTTPS.
  • Your server's clock is synced (NTP): up to 10 seconds of drift is tolerated.
  • This service allows your frontend's origin (CORS), and your API does too if it's on another origin.
  • The frontend stores both tokens after every refresh, and handles 401 (refresh, then sign in) and 403 (no access).
  • Real users are granted {{ slug }}{% if perms.users.view_user %} in Users{% endif %}.
  • The API key, if used, is in your secret store.
  • The smoke test above passes from production.
